# Test dev in GitHub Codespaces

The terminal uses the standard Codespaces Bash prompt with the current Git branch,
the non-root `vscode` user, and `/workspaces/Salon-Operation` as the project folder.
In Codespaces the prompt displays your GitHub username, for example:

```text
@shahinshabab ➜ /workspaces/Salon-Operation (dev) $
```

1. On GitHub, select the **dev** branch, then **Code → Codespaces → Create codespace on dev**.
2. Wait for the dev container to finish building. In its terminal, run:

   ```bash
   bash scripts/codespace.sh
   ```

3. Open **Ports → 8000 → Open in Browser** (or the URL printed in the terminal).
   Keep the forwarded port **Private**, its default visibility.
4. Sign in with **admin / admin**. The other fictional accounts are **manager**,
   **stylist**, and **gm**, also with password **admin**, for testing each role.

The command applies migrations, creates the demo accounts and salon/service/SOP
data, adds fictional staff tickets and sandbox AWS Google reviews, and starts the app.
Open **Tickets → Sandbox reviews** (`/reviews/google/?demo=1`) to verify appreciations, mixed
complaints, sensitive issues, review edits and publication reconciliation. The admin
can see all tickets and use Django Admin; the manager has a sample ticket and its
notification. Use the same command after Ctrl+C or reopening the Codespace.
Restart it after editing Python code; the development server uses `--noreload`.

Desktop VS Code can also forward port 8000 to `http://localhost:8000` or
`http://127.0.0.1:8000`. The startup command trusts these exact origins alongside
the Codespaces HTTPS URL, so forms work when forwarding preserves HTTPS proxy
headers. CSRF tokens and secure Codespaces cookies remain enabled. If you see
“Origin checking failed”, pull the latest `dev`, stop the server with Ctrl+C and
run `bash scripts/codespace.sh` again, then reload the login form before submitting.
No rebuild or deletion of `.devcontainer/.env` is needed. Use the private
Codespaces HTTPS URL from **Ports → 8000 → Open in Browser** if your browser does
not accept secure cookies through an HTTP localhost forward.

Repeated starts preserve accounts, changed passwords, ticket progress, and edited
sample data. PostgreSQL lives in this Codespace's own Docker volume. Deleting the
Codespace deletes its test environment; there is no production database connection.
The weak demo passwords are accepted only by this explicit development setup.

If a Codespace was created before this configuration existed, update `dev`, then
run **Codespaces: Rebuild Container** from the command palette once. No `.env` from
your server is needed. Initialization generates a separate ignored
`.devcontainer/.env` with random database credentials and Django secret, and the
exact forwarded hostname/CSRF origin. Do not copy server secrets into it.

If your existing Codespace is on a different branch, first run `git status` and
commit or stash any work you need to keep. Then switch to the shared test branch:

```bash
git fetch origin
git switch dev
git pull --ff-only origin dev
```

If `dev` does not exist locally, use `git switch --track origin/dev` instead of
`git switch dev`. Run **Codespaces: Rebuild Container** after pulling changes to
`.devcontainer`, then open a new terminal. Rebuilding retains this Codespace's
database volume and demo data. The rebuild also repairs ownership of static files
generated by the previous root terminal. The container never switches branches
automatically; the prompt reports the branch you actually have checked out.

The **Codespaces dev smoke test** GitHub Actions workflow checks this startup and
admin login on pushes to `dev` and pull requests into `dev` or `main`. It uses its own
disposable database and does not deploy the server or create a billed Codespace.

If a sandbox POST returned a committed receipt but the review is missing from the
normal inbox, check **Sandbox reviews** first. Production is the default view;
positive reviews appear in **All reviews** without an investigation ticket. A
manager still needs the matching working branch; an administrator or General
Manager can inspect all branches. The incoming `profile_key` is metadata, not an
assignment rule: map the full Google account/location identity in Django Admin's
**Google review locations** for the correct environment and an active branch.
The stock Codespaces seed uses `CS-DEMO` for this example location when no mapping
already exists. It does not infer Koppam from `profile_key: koppam`, and it does
not overwrite a mapping you already configured. Inspect the saved branch before
changing an existing mapping; reviews already assigned to a branch retain their
manager actions and are not silently moved by a replay.

Run this read-only trace **inside the Codespace that received the POST**:

```bash
python manage.py inspect_google_review \
  --review-id 56835f2d-dba5-46d4-b928-60716be0e9b5 \
  --event-id example-v3-positive \
  --environment sandbox \
  --location-name accounts/101013083477743854199/locations/12925644274742814696 \
  --expected-branch Koppam
```

The JSON reports the saved review, original receipt, database fingerprint,
read/write database match and active location-to-branch mapping, without printing
credentials or customer review text. Compare fingerprints only within the same
running deployment; this workspace, Codespaces and production use separate
PostgreSQL databases. `review: null` in another deployment does not prove the
original receipt was incorrect. The command does not create or remap anything.
