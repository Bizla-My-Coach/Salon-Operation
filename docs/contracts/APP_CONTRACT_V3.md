# App contract update for queue-only worker v3

20 October 2026. The API URL, authentication and hairship.review-result.v1 envelope are the same as APP_CONTRACT_V2.md. The app is independent of Google publication. No processing lease API, Google token, posting API or database table shared with Lambda is required. AWS now buffers results in SQS rather than DynamoDB and no EventBridge schedule is needed.

The app agent must implement the ingestion/case/dashboard requirements in APP_CONTRACT_V2.md with these changes:

1. processing.worker_version is hairship-gmb-sqs-worker-v3. Accept existing optional diagnostics and unknown future optional fields. The app receives the result envelope directly; the internal hairship.app-delivery.v1 queue wrapper is removed by Lambda.
2. Add publication.status=pending for a confirmed queued retry after Google's rate limit. Do not treat that as published or resolved. Existing submitted, published, failed, uncertain, superseded, skipped and human_review statuses retain their meanings. Moderation may remain submitted with error moderation_not_confirmed_within_retry_window after the bounded queue checks.
3. processing.result_revision is an ordering number, not a consecutive counter. Within an analysis_run_id, higher numbers supersede lower numbers. A delayed lower-confidence uncertain observation must not overwrite a higher-revision confirmed publication/failure. Some intermediate revisions may never arrive; later revisions can arrive first.
4. Enforce unique event_id and return the original committed receipt for duplicate deliveries. SQS and recovery checks can deliver the same outcome multiple times. Within a run/revision, event payloads remain stable; the same Google review version can also have different analysis_run_id values after duplicate intake/preparation retries because there is no database ledger.
5. Deduplicate business reviews/cases/issues by full source.review_name and source.review_update_time, independently of analysis IDs or transport IDs. Preserve manager actions and do not create duplicate alerts for another analysis of the same version. Reconcile publication observations separately: across runs for the same review version, prefer current confirmed Google reply evidence/timestamps over uncertain/skipped older observations; never let an unconfirmed result undo confirmed publication merely because its analysis UUID differs. Preserve all raw events needed for audit under applicable retention rules. A durably ignored obsolete event can return the documented stale receipt.
6. The result queue is a14-day delivery buffer. Its trigger stays disabled until the app URL/auth are ready. Later outages retry only application delivery and can move messages to the app-specific DLQ; app recovery/redrive does not regenerate analysis or publish Google replies.
7. Receipt shape is unchanged: event_id,status=committed,committed=true,review_record_id,case_id (when follow-up required),issues_saved_count,assignment_confirmed. Commit all incoming issues/reconciliation and assignment state before success. False assignment is valid for a saved unassigned case. HTTP202 is not a committed receipt.

Sensitive public acknowledgement is independent of manager investigation: requires_human_review=true can coexist with publication.published=true. Positive reviews with no issues are still ingested for rating/appreciation analytics and create no complaint case. Existing v2 synthetic examples show the common envelope; examples-v3 contains fixtures produced by the queue worker.

Deliver the authenticated HTTPS result URL and approved header name/secret transfer method, the app migrations and duplicate/out-of-order tests. No new app-side AWS integration is required beyond this receiving endpoint.
