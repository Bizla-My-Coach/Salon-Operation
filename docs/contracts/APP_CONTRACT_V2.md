# Application result contract: worker v2

20 October 2026. This supersedes APP_CONTRACT.md for auto_reply mode. The application's processing lease/checkpoint API is no longer needed. AWS owns its processing state and Google publication. Application failure must not block Google replies, and the app must never publish Google replies as part of receiving this event.

## Endpoint and authentication to supply

Supply one HTTPS POST URL as APP_REVIEW_RESULT_API_URL and the agreed Authorization or X-* authentication header(s), stored privately in Secrets Manager hairship/app/review-integration. Example secret shape only: {"headers":{"X-Integration-Key":"APP_APPROVED_SECRET"}}. The worker adds Content-Type: application/json and Idempotency-Key: event_id. Do not send actual secrets through documentation or chat. Redirects are not followed.

AWS explicitly POSTs a hairship.review-result.v1 JSON envelope. Its Lambda return value is an SQS acknowledgement, not the application payload. See examples-v2/*.json for synthetic payloads generated by the implemented worker.

## Envelope

- schema_version: hairship.review-result.v1.
- event_id: stable unique ID for this review version and result revision. Enforce a database uniqueness constraint. Retries send identical JSON with the same event ID.
- environment: sandbox or production. Keep sandbox separate from operational metrics/alerts.
- synthetic: true only for supplied fixtures. The deployed worker obtains actual review identities from authenticated Google notifications and sends false.
- source: provider,profile_key,account_name,location_name,review_name,review_id,review_create_time,review_update_time,fetched_at,review_snapshot. Snapshot contains star_rating,text,existing_reply. existing_reply can include comment,updateTime,reviewReplyState,policyViolation.
- processing: analysis_run_id,analyzed_at,result_revision (integer),worker_version,prompt_version,model_id. Same analysis_run_id is reused for moderation updates; result_revision increases.
- analysis: classification, generated public draft, complaint issues and human follow-up flags, plus model validation/usage diagnostics. It does not contain authoritative publication mode/state; old draft-only mode,published,publication_ready,publication_blockers fields are deliberately removed.
- publication: actual result status,published,reply_kind,reply_text,review_update_time,published_at,error_code,google_reply. Successful Google submission also includes submitted,submitted_at,visibility_confirmed,confirmation. Unknown optional fields must be retained or tolerated.

Public reply state must be read from publication, not analysis.status. The latter is model draft validation. For a sensitive acknowledgement, analysis.requires_human_review=true and publication.published=true can coexist because investigation still needs a human.

## Result statuses

| publication.status | Application meaning |
| --- | --- |
| published | Google reports APPROVED; published=true. |
| submitted | Google accepted the reply but visibility is pending/unspecified; published=false. Later revisions report approval/rejection. |
| failed | Definite API rejection, exhausted quota retries or rejected Google moderation. Display the error; do not mark solved. |
| uncertain | A write may have succeeded but could not be confirmed. Needs operational reconciliation; never automatically republish from the app. |
| skipped | Existing reply was preserved or automatic publication was disabled. error_code identifies the reason. |
| human_review | No valid automatic reply; retain review for human handling. |
| superseded | Review changed before publication, or a previously submitted reply changed/disappeared. Preserve history and process the latest version/revision. |

A published status describes Google-reported approval, not proof of the exact instant a customer saw it. google_reply preserves available source state. submitted_at/published_at use Google's reply updateTime when available.

## Required transaction

Validate supported schema/environment and trusted branch-to-location mapping. Use full review_name as the unique review identity. Save all reviews, including positive and rating-only reviews, along with the analysis, publication and history.

Create/reconcile one case per review when issues exist or case_followup_requires_human=true. Save every issue as a child task, apply branch-manager mapping, keep missing assignments in an administrator queue, and preserve human actions/resolution history when the customer edits the review. The model's allegations are not confirmed investigation findings. Sensitive injury_or_health issues are urgent; human_review_scope concerns investigation/substantive response, not approval of the generic public acknowledgement.

Use event_id for delivery deduplication. Use source.review_update_time to reconcile review versions; within the same review version/analysis, apply only the greatest processing.result_revision to current publication state. Delivery can be duplicated or out of order, and a later moderation revision can arrive first. Do not create duplicate cases/issues/alerts for those later revisions. Older dispositions must not undo manager work or newer publication state.

Commit the review, applicable case, every issue, assignment and delivery receipt before returning success. Send manager notifications via the app's own durable mechanism after that commit. Publication and customer issue resolution are separate states.

## Required successful response

HTTP200 or201, JSON <=128KiB:

```json
{
  "event_id": "ECHO_REQUEST_EVENT_ID",
  "status": "committed",
  "committed": true,
  "review_record_id": "review_123",
  "case_id": "case_456",
  "issues_saved_count": 1,
  "assignment_confirmed": true
}
```

case_id may be null for positive reviews without a case. It is required when analysis.case_followup_requires_human=true. review_record_id and required case_id must be nonempty ASCII alphanumeric/underscore/hyphen strings <=256 characters; serialize numeric IDs as strings. issues_saved_count must equal the number of incoming analysis.issues saved/reconciled for this analysis, not the historical issue total. assignment_confirmed is a real Boolean based on saved assignment, never a model assumption. A durably saved unassigned case returns false. Return the same receipt for duplicate event IDs, without repeating side effects.

For a durably recorded older event intentionally ignored because a newer version/revision exists, HTTP200 may return:

```json
{"event_id":"ECHO_REQUEST_EVENT_ID","status":"stale","committed":true}
```

HTTP202 does not prove persistence under this contract. Network errors,5xx,invalid receipts or uncommitted responses cause AWS outbox retry with backoff independently of Google publication. AWS retains this retry buffer for28days; app outages must be recovered within that window.
